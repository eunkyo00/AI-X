## 이번에 보완한 부분

1. 문서에서 등록된 파일명만 검색하던 방식을 보완했다. 명시적 파일명·경로, 따옴표·백틱 경로와 Markdown 파일 링크를 추출하며 미등록 대상도 남긴다.
2. 문서의 명시적 경로가 유일한 등록 파일 경로와 일치하면 파일 ID로 연결한다. 파일명만 있거나 경로가 중복되면 확정하지 않는다.
3. 같은 참조가 반복되면 등장 위치마다 근거를 저장한다. 동일 파일명의 등록 후보가 여러 개라는 이유로 같은 문서 위치의 근거가 중복 생성되던 현상을 제거했다.
4. Python 여러 줄 호출의 전체 구문과 `to_csv(path_or_buf=...)` 저장 경로를 기록한다.
5. 웹 URL은 로컬 파일 참조에서 제외한다. 근거 위치와 원문, 상태는 기존 SQLite 관계 테이블과 CSV에서 조회할 수 있다.

## 실제 데이터 실행 결과

기존 `Role03/input/source.json`에 기록된 입력 사본을 사용했다. 파일 161개, 추출 성공 149개, 로컬 원본 확인 161개다.

| 관계 | 연결 확정 | 불확실 | 대상 미등록 |
| --- | ---: | ---: | ---: |
| 코드 읽기 | 4 | 0 | 49 |
| 코드 저장 | 0 | 0 | 3 |
| 문서 명시적 참조 | 15 | 22 | 70 |
| 합계 | 19 | 22 | 122 |

총 163건이다. 이전 226건과의 차이는 중복 후보별 문서 근거 제거 및 미등록·경로 참조 추출 변경에 따른 것이므로 단순 누락률로 비교하면 안 된다.

- `resolved`: 경로로 유일한 파일 ID를 확인. 대상 ID 저장.
- `ambiguous`: 파일명 후보나 중복 경로 때문에 확정 불가. 대상 ID는 비워 둠.
- `missing`: 등록 목록에서 대상을 확인할 수 없음. 실제 디스크 부재를 뜻하지는 않음.

예: `F129` 노트북의 4번째 코드 셀 3행에서 `../../../data/birds.csv` 읽기를 발견해 `F155`로 연결하고 구문을 저장했다. 코드에 적힌 관계이며 실행·실제 사용 사실을 의미하지 않는다.

## 데이터 기준과 남은 한계

GitHub 최신 Role01 메타데이터는 158개이며, 기존 161개 사본과 비교하면 `.Rhistory` 1개와 `.DS_Store` 2개가 제외되어 있고 나머지 메타데이터 행은 동일했다. 이번 DB는 출처가 기록된 기존 161개 사본 기준이며 최신 CSV로 교체했다고 표시하지 않았다. 최신 입력을 채택할 때는 본문 CSV도 같은 버전으로 맞춰 검증한 뒤 재생성해야 한다.

기존 파일 크기 불일치 36개와 텍스트 추출 미성공 12개는 그대로 남아 있다. PDF·Word·PPT의 본문 추출은 Role01의 기존 CSV를 사용하며, 이번 역할은 그 본문에서 참조를 추출·저장하는 것이다.

동적 변수 경로, 여러 줄 R 호출, 작업 디렉터리 변경 추적은 지원하지 않는다. 미등록 문서 파일명은 지원 확장자에 한정되며 공백이 있으면 따옴표·백틱·Markdown 링크가 필요하다. 문서 위치는 추출 본문의 문자 오프셋으로 원본 쪽 번호가 아니다.

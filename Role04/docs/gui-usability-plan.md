# GUI·사용성 담당 실행 계획

> 2026-10-19 구현 현황: GUI는 웹 방식으로 전환했다. 초기 계획은 아래에 보존하며, 최신 완료/대기 구분은 [GUI 인수인계](gui-handoff.md), 팀원 API 초안은 [연결 규격](api-contract.md)을 참고한다. 실제 서비스 통합과 외부 사용자 평가는 아직 완료되지 않았다.

기준: AIX_Plan_Balanced_Roles.pdf 2·5·6·7쪽과 저장소 README.
작성일: 2026-09-28. 아래 세부 인터페이스·일정 배분·사용성 기준은 실행을 위한 제안이며 팀 합의 사항은 아니다.
이번 단계는 할 일 구체화다. 툴 설치는 다음 단계에서 진행한다.

## 1. 담당 범위와 최종 결과

사용자가 파일을 등록하고, 기억하는 상황으로 검색하고, 결과·근거·관련 파일을 확인한 뒤 원본 파일 또는 저장 폴더를 여는 흐름을 구현한다.

| 내가 구현할 것 | 팀원에게 받을 것 |
| --- | --- |
| 파일/폴더 선택, 등록 목록, 처리 상태 표시 | 3번: 등록 처리, 파일 ID, 메타데이터, 단계별 진행·실패 정보 |
| 검색 입력, 결과 목록, 근거·관련 파일 표시 | 1번: 검색 순위, 질의 해석, 근거, 관련 파일과 관계 유형 |
| 원본 열기·저장 위치 열기, 사용자 오류 안내 | 3번: 파일 ID에 대응하는 최신 경로·존재 여부 |
| 사용성 시나리오, 관찰 기록, UI 오류 수정 | 2번: 대표 질문·파일 세트, 정답 검수, 평가용 시나리오 |

검색 점수 계산·임베딩·파일 내용 추출·DB 구조·정답 데이터 구축은 해당 담당자가 소유한다. GUI는 결과를 전달받아 표현한다. 통합 오류는 함께 해결한다.

## 2. 먼저 팀과 결정할 항목

- [ ] 시연 운영체제 확정: 현재 개발 환경은 macOS이며 팀의 시연 OS는 미확인.
- [ ] 첫 완성본에서 지원할 확장자 확정. PDF·CSV·PPTX·TXT·Python·R은 후보이며 실제 지원 여부는 3번과 합의.
- [ ] 등록의 의미 확정: 원본을 복사하는지, 기존 경로를 참조하는지. 계획서 취지에 따라 경로 참조를 우선 제안.
- [ ] 등록 완료와 검색 준비 완료를 구별할지 합의. 추출 완료만으로 검색 가능하다고 표시하지 않는다.
- [ ] Python 내부 서비스 호출 방식과 데이터 형식 합의. 단일 Python 데스크톱 앱이라면 HTTP 서버 없이 시작 가능.
- [ ] 1번에게 예시 검색 응답, 3번에게 예시 등록 이벤트, 2번에게 대표 작업 세트 1개 요청.

완료 기준: 지원 범위·OS·호출 방식·샘플 응답을 팀 문서에 기록하고 각 담당자가 확인한다.

## 3. 화면 구성

별도 창을 많이 만들기보다 하나의 메인 창에 다음 영역을 배치한다.

| 영역 | 필수 내용 |
| --- | --- |
| 등록 영역 | 파일 추가, 폴더 추가, 선택 경로, 등록 목록, 성공·실패·건너뜀 수 |
| 검색 영역 | 자연어 입력, 검색 버튼, 예시 문장, 검색 중 상태 |
| 결과 영역 | 순위, 파일명, 형식, 역할, 경로, 요약 근거, 선택 상태 |
| 상세 영역 | 선택한 파일의 근거, 관련 작업, 관련 파일, 확인/추정 구분 |
| 동작·상태 영역 | 파일 열기, 저장 위치 열기, 현재 처리 상태, 오류와 재시도 |

복잡한 관계 그래프는 후순위다. 첫 완성본은 목록과 관계 라벨로 표현해도 된다.

## 4. 구현 작업 목록 — 아래 순서로 진행

### GUI-01. 사용자 흐름과 화면 초안
- [ ] `파일 선택 → 분석/인덱싱 → 검색 → 결과 선택 → 근거/관련 파일 확인 → 열기` 흐름 작성.
- [ ] 첫 실행, 등록 중, 검색 준비, 검색 중, 결과 있음, 결과 없음, 오류 화면을 간단히 그린다.
- [ ] 대표 질의는 “지난달 R 과제할 때 사용했던 데이터”로 시작한다.
- [ ] 긴 파일명·한글 경로·근거가 없는 결과의 배치도 정한다.
- 산출물: 화면 초안, 상태별 문구표.
- 완료 기준: 팀원이 초안을 보고 각 버튼의 동작과 다음 화면을 설명할 수 있다.

### GUI-02. 팀 간 데이터 계약과 예시 데이터
- [ ] 아래 5절의 함수와 데이터 필드를 팀원과 조정한다.
- [ ] 정상 결과, 빈 결과, 근거 누락, 관련 파일 없음, 오류, 지연 응답 예시를 만든다.
- [ ] 실제 서비스와 같은 형태로 응답하는 MockService를 만든다.
- 산출물: 서비스 인터페이스 문서, 예시 응답, MockService.
- 완료 기준: 검색 엔진·DB 없이도 모든 UI 상태를 확인할 수 있다.

### GUI-03. PySide6 앱 기본 골격
- [ ] 메인 창, 등록·검색·결과·상세 영역을 만든다.
- [ ] UI 코드와 서비스 호출 코드를 분리한다.
- [ ] 창 크기 변경, 최소 크기, 긴 텍스트 생략·전체 보기 처리를 넣는다.
- [ ] Enter 검색, Tab 이동, 명확한 포커스 표시를 넣는다.
- 산출물: 예시 데이터로 실행되는 앱.
- 완료 기준: 실행 명령 하나로 창이 열리고 기본 흐름을 조작할 수 있다.

### GUI-04. 파일 등록 화면
- [ ] 파일 다중 선택과 폴더 선택을 구현한다. 드래그앤드롭은 후순위.
- [ ] 등록 전 선택 목록과 경로를 보여준다.
- [ ] 지원하지 않는 형식·중복·권한 부족은 3번 서비스의 처리 결과에 맞춰 표시한다.
- [ ] 대기/분석 중/인덱싱 중/검색 가능/실패 상태와 개수를 표시한다.
- [ ] 일부 실패 시 성공한 항목을 유지하고 실패 항목·사유·재시도를 제공한다.
- 산출물: 등록 목록과 진행·실패 표시.
- 완료 기준: 일부 파일이 실패해도 전체 앱을 다시 시작하지 않고 성공·실패를 구별할 수 있다.

### GUI-05. 검색 입력과 결과 목록
- [ ] 공백 질의는 실행하지 않고 입력 안내를 표시한다.
- [ ] 검색 버튼과 Enter가 같은 동작을 수행하게 한다.
- [ ] 검색 중임을 표시하고 중복 실행 정책을 정한다.
- [ ] 1번이 반환한 순위를 유지하고 파일명·역할·경로·근거를 표시한다.
- [ ] 0건이면 조건을 바꾸거나 등록 상태를 확인하도록 안내한다.
- [ ] 연속 검색 시 이전의 늦은 응답이 새 결과를 덮어쓰지 않게 요청 ID를 확인한다.
- 산출물: 검색 입력과 결과 선택 기능.
- 완료 기준: 정상·빈 결과·실패·연속 요청에서 화면이 현재 검색과 일치한다.

### GUI-06. 근거·관련 파일 상세
- [ ] 결과 선택 시 상세 패널을 갱신한다.
- [ ] 내용·시간·역할·참조 근거를 읽기 쉬운 문장으로 표시한다.
- [ ] “코드에서 파일 참조 확인”과 “같은 작업으로 추정”을 텍스트로 구별한다.
- [ ] 수정 시각을 실제 사용 시각으로 표현하지 않는다.
- [ ] 코드의 저장 구문을 실제 생성·실행 사실로 단정하지 않는다.
- [ ] 관련 파일의 역할·관계·근거를 표시하고 해당 파일로 이동할 수 있게 한다.
- [ ] 근거·역할·시간이 없으면 만들어 채우지 않고 없음/알 수 없음으로 표시한다.
- [ ] 점수를 확률로 보정한 근거가 없으면 “정확도 95%” 같은 표현을 사용하지 않는다.
- 산출물: 파일 상세·관련 파일 목록.
- 완료 기준: 사용자가 연결 근거와 추정 여부를 구분할 수 있다. 초기 직접 연결 1단계 범위는 1번 서비스가 결정한다.

### GUI-07. 파일·저장 위치 열기
- [ ] 파일 ID에 대응하는 경로로 파일과 폴더를 연다.
- [ ] 존재 여부·접근 가능 여부를 확인하고 실패 시 경로와 해결 행동을 안내한다.
- [ ] 한글·공백이 포함된 경로를 검증한다.
- [ ] 일반 문서는 OS 연결 앱으로 열고 Python·R·실행 파일은 실행하지 않는 열기 정책을 정한다.
- [ ] 코드 파일은 안전한 텍스트 보기 또는 확인된 편집기로 연다. 안전한 편집기가 없으면 폴더 열기로 안내한다.
- 산출물: OS별 열기 어댑터와 실패 안내.
- 완료 기준: 실제 시연 OS에서 문서·코드·없는 파일의 동작을 점검하며 원본 변경·코드 실행이 발생하지 않는다.

### GUI-08. 멈춤 방지와 오류 복구
- [ ] 파일 분석·인덱싱·검색을 GUI 메인 스레드 밖에서 수행한다.
- [ ] Qt signal로 UI를 갱신하고 worker에서 위젯을 직접 조작하지 않는다.
- [ ] 전체 개수를 알면 개수 기반 진행률, 모르면 처리 중 표시를 사용한다.
- [ ] 오류는 “무슨 일인지 + 다음 행동”으로 표시하고 상세 오류는 로그로 분리한다.
- [ ] worker 실행 중 앱 종료 시 안전하게 정리한다.
- [ ] 취소 기능은 서비스가 실제 취소를 지원할 때 연결한다. 결과를 숨기는 동작을 취소 완료로 표현하지 않는다.
- 산출물: 비동기 연결, 사용자 오류 문구, 진단 로그.
- 완료 기준: 지연·오류 예시 응답 중에도 창 이동·크기 변경이 가능하며 복구 후 다시 검색된다.

### GUI-09. 실제 서비스 통합
- [ ] MockService를 1번·3번의 실제 서비스로 교체한다.
- [ ] 파일 ID·경로·역할·근거 필드가 끝까지 일치하는지 확인한다.
- [ ] 등록 완료 후 검색 인덱스 준비 여부를 반영한다.
- [ ] 2번이 검수한 대표 작업 세트로 등록부터 열기까지 점검한다.
- [ ] 오류를 UI 표시 문제, 서비스 응답 문제, 데이터 문제로 나누어 담당자에게 전달한다.
- 완료 기준: 실제 파일과 실제 검색 결과로 전체 흐름이 연결된다. 예시 응답 시연은 통합 완료로 세지 않는다.

### GUI-10. 사용성 점검·시연 준비
- [ ] 개발자 외 사용자 3~5명에게 설명을 최소화하고 주요 과제를 수행하게 한다. 인원은 제안이다.
- [ ] 파일 등록, 자연어 검색, 근거 설명, 관련 코드 찾기, 파일/폴더 열기를 관찰한다.
- [ ] 성공 여부·소요 시간·막힌 위치·잘못 누른 버튼·도움 요청을 기록한다.
- [ ] 확인된 참조와 추정 관계의 차이를 사용자에게 설명해 보게 한다.
- [ ] 파일 누락·0건·일부 등록 실패의 복구 행동이 이해되는지 확인한다.
- [ ] 중요한 문제부터 수정하고 같은 과제로 다시 확인한다.
- [ ] 새 환경 설치 방법, 실행법, 알려진 한계, 3분 시연 순서를 문서화한다.
- 산출물: 사용성 기록표, 수정 목록, 실행 안내, 시연 시나리오.
- 완료 기준 제안: 전체 흐름을 막는 오류 0건, 실제 시연 환경에서 재실행 포함 연속 3회 시연 성공. 이는 계획서의 기존 수치가 아닌 내부 품질 기준 제안이다.

## 5. 다른 담당자와 합의할 데이터 계약 초안

아래 명칭은 제안이다. 실제 구현 전에 1번·3번과 맞춘다. HTTP API 도입을 전제로 하지 않는다.

| 호출/이벤트 | 필요한 입력·출력 | 소유자 |
| --- | --- | --- |
| register_paths(paths) | 선택 경로 목록 → job_id | 3번, 인덱싱 단계는 1번과 조율 |
| registration_progress | job_id, 단계, 완료/전체 수(알 수 없으면 null), 성공/실패/건너뜀 수, 항목별 오류 | 3번·1번 |
| search(query, request_id) | 질의 → request_id, 정렬된 결과, 선택적 질의 해석, 경고 | 1번 |
| get_related(file_id) | 관련 파일, 관계 유형, 근거, 확인/추정 구분 | 1번 |
| resolve_file(file_id) | 최신 로컬 경로, 존재 여부 | 3번 |

검색 결과 최소 필드: file_id, name, path, extension, role(없으면 null), rank, evidence[].
근거 최소 필드: kind, text, source_file_id(없으면 null), certainty(확인/추정).
관계 최소 필드: source_file_id, target_file_id, relation_type, evidence[], certainty.
오류 최소 필드: code, 사용자용 설명, 재시도 가능 여부. 원본 파일 내용은 기본 로그에 남기지 않는다.
UI는 반환된 순서를 유지하며 검색 점수·관계 판단을 자체 재계산하지 않는다.

이번에는 설치하지 않는다. 설치 단계에서 기존 도구·팀 Python 버전·시연 OS를 확인한 뒤 호환 버전을 고정한다.

# AI-X 프로젝트 전체 개발 및 실험 기록

기준: `eunkyo00/AI-X`의 `main`, [6606aee277c154051d3d94be07842b85bed1a687](https://github.com/eunkyo00/AI-X/commit/6606aee277c154051d3d94be07842b85bed1a687). 조사일: 2026-11-23, 한국 시간.

이 문서는 저장소에 남은 구현, 평가 산출물, 보고서와 이 커밋까지의 142개 커밋을 대조한 개발 기록이다. README의 주차별 계획은 완료 증거로 사용하지 않았다. 개발일은 보고서에 명시된 경우에만 기록하고, 그 외 날짜는 커밋 기록일로 표시한다. 커밋 작성·반영 시각은 실제 개발 시작·완료일과 같다고 가정하지 않는다. 파일 이동, 폴더 평탄화, 실행 파일 묶음 정리는 기존 활동에 합쳤다. 별도 정리 브랜치와 로컬 미커밋 작업은 범위 밖이다.

수치는 원본 CSV·JSON·보고서의 값을 사용하며, CSV에서 합산한 값은 재집계임을 표시한다. 과거 결과에 현재 정답표를 소급 적용하지 않는다. GUI가 준비하는 백엔드 스냅샷과 저장소 최신 데이터는 서로 다르다. 개인별 담당 배정은 확인할 근거가 부족하므로 Role 단위로 설명한다.

## 1. 프로젝트 개요

### 1.1 개발 배경과 기술적 목적

파일이 많아지면 이름과 저장 위치보다 “지난달 R 과제에 사용한 데이터” 같은 작업 상황이 더 잘 기억된다. AI-X의 목표는 이런 자연어 단서를 파일 내용, 생성·수정 시각, 프로젝트·역할, 파일 간 참조와 연결하여 원하는 파일을 다시 찾는 것이다. 관련 자료도 함께 제시하되, 정적으로 확인한 참조와 유사도에 의한 추천을 구분한다. [최상위 README](../README.md)

초기 목표에는 작업별 파일 세트와 관계 복원, 키워드·의미·맥락 검색의 비교가 포함된다. 실제 개발은 파일 목록·본문 추출, E5 의미 검색, 설명·시간 조건 실험, 분류 모델, 정적 참조 DB, 웹 GUI와 자동 갱신의 순서로 확장되었다. 현재 프로젝트 라벨은 주로 과목 구분이다. 과목별 묶음을 사용자의 실제 작업 세션 복원과 동일시할 수 없다.

### 1.3 전체 동작 흐름과 역할 연결

1. 파일 선택·폴더 연결로 앱 보관본을 만들고 파일 ID와 메타데이터를 관리한다. 연결 원본은 읽기만 한다.
2. 형식별 본문을 추출하고, 기존 수동 설명을 보호하면서 필요한 설명·프로젝트·자료 유형·시간 정보를 만든다.
3. SQLite에 파일과 정적 참조 근거를 저장하고, 본문·설명 기반 임베딩 인덱스와 관계 추천을 갱신한다.
4. 자연어 질의에서 시간과 명시 라벨 조건을 분리하고, 조건을 만족하는 파일을 의미 유사도로 정렬한다.
5. GUI가 상위 결과, 대응 본문, 설명·시간·분류 정보와 별도의 관련 파일을 표시한다. 원본 다운로드·미리보기와 재등록·동기화 상태도 제공한다.

이는 최신 GUI의 흐름이다. `update_pipeline.py`는 목록→본문→설명→인덱스, `update_pipeline_integrated.py`는 여기에 자동 분류를 추가한다. `update_data.update(integrated=True)`는 임시 공간에서 통합 파이프라인을 실행하고 DB·V5 관계까지 만든 뒤 결과를 게시한다. 명령행 기본 `update_data.py`와 GUI의 선택적 Qwen 처리 범위는 같지 않다. [기본 파이프라인](../update_pipeline.py), [통합 파이프라인](../update_pipeline_integrated.py), [GUI 갱신 어댑터](../Role04/scripts/search_api.py)

## 3. 역할별 개발 및 실험 기록

### 3.1 Role01 — AI 검색 엔진

#### 초기 의미 검색과 평가 기반

초기 [search_model(prior).py](../Role01/search_model%28prior%29.py)는 본문을 청크로 나누어 E5로 검색하는 대화형 구현이다. [search_model.py](../Role01/search_model.py)는 빈 본문·중복 ID를 걸러내고 파일별 최고 청크 점수로 결과를 묶으며, 평가 질문과 정답 파일명을 진단한다. [search_model_modified.py](../Role01/search_model_modified.py)는 정답 `file_id` 기반 평가와 디스크 임베딩 캐시를 사용한다. 서로 다른 경로의 README·노트북·과제 문서가 같은 이름을 쓰기 때문에 파일명만으로 채점할 수 없었던 문제에 대응한 흐름이다.

파일명·본문 키워드 기준선은 초기 계획에 있지만, 저장소에는 이 의미 검색 실험과 직접 비교할 독립 키워드 기준선 결과표가 확인되지 않는다. GUI의 브라우저 보관 파일명 검색과 재정렬의 파일명 보조 점수는 구현되어 있으나, 이를 독립 키워드 검색 평가로 간주하지 않았다.

#### 재정렬·설명·시간·라벨의 추가

상위 30개 후보를 최고 청크·상위 3청크 평균·파일명 일치로 재정렬했으나 Hit@5는 그대로였다. 실패 순위 진단은 후보 30개 밖의 정답도 보여 주었다. 이후 각 청크에 파일 설명을 넣은 실험은 보존된 158질의에서 모두 적중했다. 설명이 질의와 직접 대응할 수 있고 동일 질문으로 개발한 결과이므로 독립 최종 성능으로 확대하지 않는다. [재정렬](../Role01/search_model_rerank.py), [설명 실험](../Role01/search_model_description.py), [실패 순위 진단](../Role01/search_rank_diagnosis.py)

시간 검색은 생성일·수정일 파싱, 기간 `[시작, 종료)` 필터, 시간 표현을 제거한 의미 질의로 구성된다. 현재 엔진은 명시 날짜, 월·연도, 오늘·어제·지난달·최근 N일/주/개월 등의 표현을 지원하며 잘못되거나 모호한 표현을 오류로 알린다. [search_engine_time.py](../Role01/search_engine_time.py)는 별도 시간 확장 구현으로 남아 있고, GUI는 [search_engine.py](../Role01/search_engine.py)를 사용한다. 시간 전용 평가와 일반 질의를 나누는 과정에서 정답 ID도 교정되었으므로 점수 변화의 원인을 분리해야 한다.

최신 엔진은 수동 라벨을 우선하고, 확인 불필요 자동 예측만 검색 필터로 쓴다. 질의에 등장한 등록 프로젝트·역할을 가장 긴 라벨부터 하나씩 선택한다. 이는 자유로운 작업 의도 추론 모델이 아니며 복수 역할 표현에 오해석 가능성이 남는다. 순위 계산은 의미 유사도이고, 관계 추천은 별도로 반환한다.

#### 관계 추천의 다섯 단계

| 버전 | 바꾼 요소 | 문제 대응·남은 한계 |
| --- | --- | --- |
| V1 | 인용 문자열의 경로·파일명 참조, 최대 10개 파일 폴더의 약한 동일 폴더 관계 | 실제 실행 관계를 증명하지 않으며 폴더만으로 작업을 확정할 수 없음 |
| V2 | 상대경로 해석, 외부 URL 제외, 불확실 파일명 후보, 문자 2~4그램 TF-IDF | 파일명×3·설명×2·프로젝트·본문 앞 5,000자로 비교; 다른 확장자 후보만 최대 3개, 임계값 0.36 |
| V3 | 청크 E5 평균을 정규화한 파일 벡터, 유사도 0.80 이상 상위 5개 | 내용은 비슷하나 실제 작업이 다른 파일을 구분할 단서 부족 |
| V4 | 의미·프로젝트·역할·시간·폴더 결합, Role03 `resolved` 참조 우선 | 개발 지표는 높아졌지만 검토 집합 Recall·MRR은 악화 |
| V5 | 같은 프로젝트의 파일명 주차 추출, 가중치 재조정 | 검토 Recall 개선; MRR은 V3보다 낮아 모든 지표 개선은 아님 |

V4 점수는 의미 0.50·프로젝트 0.20·역할 0.15·시간 0.10·폴더 0.05이다. V5는 의미 0.60·프로젝트 0.10·역할 0.10·시간 0.05·폴더 0.05·동일 주차 0.10이다. V4/V5 모두 비직접 후보 임계값은 0.55, 직접 참조 우선 상위 5개이다. 주차는 `weekN`, `N주차`, `time_series_analysisN` 패턴을 쓰며 시간 정보에서 주차를 학습하는 기능과 다르다. [V1](../Role01/file_relations.py), [V2](../Role01/file_relations_v2.py), [V3](../Role01/file_relations_v3.py), [V4](../Role01/file_relations_v4.py), [V5](../Role01/file_relations_v5.py)

#### 재사용 엔진과 증분 갱신

API용 엔진 분리 후 전체 입력 해시의 `.npy` 캐시를 도입했고, 이후 [refresh_search.py](../Role01/refresh_search.py)가 파일 ID·모델·실제 passage 입력 해시에 따른 파일별 캐시를 만들었다. 공통 인덱스의 모델명·입력 서명·청크 순서·벡터 수를 확인하여 과거 인덱스 사용을 거절한다. 갱신 중 검색을 막고 다음 검색에서 변경을 재로딩한다. [search_engine_integrated.py](../Role01/search_engine_integrated.py)는 통합 구현의 별도 보존본이며 현재 GUI 진입점과 구분한다.

### 3.2 Role02 — 데이터 분류 및 평가

#### 데이터·정답 구성과 평가 오류의 발견

초기 자료에는 딥러닝·시계열분석·졸업작품·한국근현대사역사기행과 Microsoft 데이터사이언스 자료가 들어간다. 이후 금융·신규 강의·등록 테스트 표본을 추가했다. 데이터셋 안의 YOLO·라즈베리파이·음성 안내 Python/R 코드는 검색 대상 자료이며, 해당 기능을 AI-X의 검색 서비스 기능으로 기록하지 않는다. [검색 대상](../Role01/dataset/files/), [메타데이터](../Role01/metadata.csv)

158질의의 [실패 보고](../Role02/search_fail.txt)는 동명 파일 오채점, 비슷한 강의·코드의 경쟁, 추출 누락을 구분하도록 요구한다. 이후 194질의와 여러 정답표 백업이 남았다. [실패 감사](../Role01/failed_queries_audit.csv)는 과거 ID가 현재 다른 파일을 가리키는 사례 57행을 보존한다. 이 57행은 표본 감사이며 전체 오류율이 아니다. README가 요구하는 작업 단위 개발·최종 분리는 방향성이고, 실제 프로젝트 분류 실험은 파일 단위 교차검증이다.

#### 프로젝트 분류 v1→v2→v3.1

v1은 정답 프로젝트·폴더 경로를 제외한 파일명·확장자·설명·본문을 임베딩하고, 파일별 최대 네 개 1,200자 조각을 평균하여 로지스틱 회귀를 학습한다. 5겹 교차검증에서 5개 과목 158개를 평가했다. 신규 과목 표본이 없어 정답 예측 신뢰도의 하위 5%로 초기 거절 기준을 잡았다. [v1 입력](../Role02/project_classifier.py), [학습](../Role02/train_project_classifier.py)

[v2 입력](../Role02/project_classifier_v2.py)은 description을 제외하며 [v2 학습기](../Role02/train_project_classifier_v2.py)가 이를 사용한다. 다만 v2 유틸리티의 기본 산출 디렉터리·모델 경로는 v1 폴더를 가리키고, 보존된 v1/v2 JSON은 같은 정확도·F1·임계값이다. 실행 옵션·산출물 출처를 모두 고정한 비교 기록이 없어 이 JSON만으로 설명 제거의 효과를 확정하지 않는다. 통제된 설명 비교는 실험 6의 A/B 기록을 기준으로 한다.

v3는 본문·설명·파일명을 별도로 임베딩한 후 가중 연결하고, 분류 확률·1/2순위 차이·클래스 중심 유사도·중심 간 차이·두 예측의 일치를 검사한다. v3.1은 `C=10`과 검증 분포 기반 기준을 적용한다. 기존 클래스 내 최고 예측이 맞는 것과 자동 확정 여부는 별개다. 기존 과목 100% 선택 정확도에도 10/158개는 자동 확정하지 않았다. [v3.1 학습](../Role02/train_project_classifier_v3.py), [프로젝트 안내](../Role02/PROJECT_CLASSIFIER.md)

#### 자료 유형·시간·설명 생성

자료 유형은 세부 역할을 강의자료·실습자료·코드·과제·데이터·안내자료의 6종으로 정규화한다. 수동 description에 정답 역할이 직접 쓰인 누출을 피하려고 분류 입력에서 제외한다. 파일명·확장자가 명백하면 규칙을 우선하고, 나머지는 임베딩 분류기를 쓴다. 전체 정확도와 확인 없이 채택한 부분집합의 정확도·커버리지를 함께 남겼다. [유형 학습](../Role02/train_role_classifier.py), [통합 예측](../Role02/classify_file_metadata.py)

시간 분류는 학습 모델이 아니라 명시 activity 시각→수정 시각→생성 시각 순서로 연·월·분기·반기·계절을 만드는 규칙이다. 달력 정보의 생성은 가능하지만 실제 파일 사용 시점을 알 수는 없다. [시간 분류기](../Role02/time_classifier.py), [시간 평가기](../Role02/evaluate_time_classifier.py)

설명 생성기는 파일명과 본문 앞 4,000자를 Qwen에 전달하고, 프로젝트 정답·폴더 경로를 프롬프트에 넣지 않는다. 수동 설명을 보존하며 본문 해시로 재생성을 줄이고 5개 성공마다 중간 저장한다. 병합·진행 CSV와 신규 파일 시험 산출물도 남아 있다. 다만 [과거 통합 시험](../Role02/test_integration.py)은 현재 생성기에 없는 `merge_existing_descriptions`·`fill_descriptions` 함수를 호출하므로 현재 회귀 테스트 통과 근거로 사용할 수 없다. [설명 생성기](../Role02/description_generator.py), [설명 병합](../Role02/merge_descriptions.py)

#### 자동화와 GUI 연결

초기 [최근접 라벨 전파](../Role01/auto_label.py)는 신규 파일을 기존 파일 벡터와 가장 가까운 프로젝트로 배정하여 신규 클래스 거절 장치가 없다. [자동 실행기](../Role01/automation_code/auto_classify.py)는 파일별 분류 CLI를 호출하는 단계다. 현재 [classify_metadata.py](../Role02/classify_metadata.py)는 수동/예측 열을 분리하고 자동 결과를 별도 CSV에 저장한다. 기본 실행은 기존 ID의 예측을 재사용하므로 변경 파일 재계산에는 `--force` 또는 호출자의 선처리가 필요하다. ### 3.3 Role03 — 파일 처리 및 데이터베이스

#### 등록·추출·식별자 관리

최초 [file_inform.py](../Role01/file_inform.py)는 스캔 때 ID를 순서대로 부여하는 방식이다. 이후 [file_reload_code.py](../Role01/file_reload_code.py), [file_reload_sorted.py](../Role01/file_reload_sorted.py), [file_reload_append_only.py](../Role01/file_reload_append_only.py)로 경로 정규화, 기존 ID·수동 열 보존, 정렬·백업을 보완했다. Windows 경로와 한글 정규화, 실행 위치와 무관한 경로 처리가 필요했다. 이동·이름 변경은 경로 기준상 새 파일이며 내용 기반 동일 파일 추적은 구현 증거가 없다. 기본 갱신기는 ID 상태 파일을 쓰지만 append-only 경로와 GUI의 ID 예약은 별도 구현이므로 같은 보장을 무조건 적용하지 않는다.

생성 시각은 ZIP NTFS 확장 정보, 기존 값, 파일시스템 제공 시각 등을 활용한다. 복사·다운로드·압축 해제 시각을 실제 작업일로 간주하지 않는다. 본문 추출 범위와 제한은 다음과 같다. [추출 코드](../Role01/extract_content.py)

| 형식 | 처리 | 제한·예외 |
| --- | --- | --- |
| TXT/MD/JSON/PY/R/HTML/CSS/JS/SQL | UTF-8 텍스트 읽기 | 디코딩 오류는 대체 문자 처리; 코드 실행하지 않음 |
| IPYNB | 코드·Markdown 및 저장된 텍스트/HTML 출력 추출 | 노트북 실행하지 않음 |
| CSV/TSV | UTF-8-SIG·CP949 시도, 구분자별 읽기 | 최대 100행 |
| XLSX | 시트별 셀 값 | 시트별 최대 100행, 저장된 계산 값 사용 |
| PDF | 텍스트 레이어 우선, 빈 페이지는 kor+eng OCR | 최대 100페이지, Tesseract 필요 |
| DOCX/PPTX | 문단·슬라이드·표 텍스트 | 임의 바이너리·이미지 본문 인식 보장 없음 |
| 공통 | 본문 길이 제한·처리 상태 기록 | 약 100,000자 이후 생략 안내; 미지원·빈 본문·오류 구분 |

이미지·영상·시스템/기록 파일은 등록 목록에서 제외하는 경로가 있다. GUI의 신규 이미지/OCR 전용 문서 검색 등록은 지원하지 않으며 기존 성공 본문만 원본 해시 일치 시 재사용한다. 추출기 자체의 OCR 가능성과 GUI 등록 지원을 구분한다.

6주차 구현은 읽기 전용 입력 사본의 ID를 유지하여 `files`, `relations`, `provenance` 테이블을 만들었다. CSV의 빈/중복 ID, ID 집합 및 파일명·경로 불일치를 갱신 전에 거절한다. 원본 해시, 추출 상태, 참조 종류·원문·위치를 저장하며 `get_file`·`get_relations`로 조회한다. [DB 구현](../Role03/file_db.py), [조회 예제](../Role03/query_example.py), [입력 출처](../Role03/input/source.json)

Python은 AST의 리터럴 경로 호출을, 노트북은 코드 셀별 AST를 분석한다. R은 지원 읽기·쓰기 호출의 한 줄 문자열 경로를 분석한다. 문서는 파일명·따옴표·백틱·Markdown 경로를 수집한다. 10월 19일에는 미등록 문서 참조, 반복 위치, 공백 경로, Python 여러 줄/키워드 인자, 외부 링크 오탐을 보완했다.

상태는 `resolved`(유일한 경로의 파일 ID 확인), `ambiguous`(파일명 후보·중복 경로로 확정 불가), `missing`(등록 대상 없음)이다. `missing`은 디스크 소실과 같지 않다. 동적 경로·변수, 여러 줄 R 호출, 작업 디렉터리 변경 추적은 미지원이며 정적 저장 구문은 실제 생성 사실이 아니다. 문서 위치는 추출 텍스트 오프셋으로 원본 PDF 쪽 번호가 아니다.

## 4. 주요 실험 및 성능 비교

### 4.0 지표와 비교 기준

Hit@5는 정답이 상위 5개 안에 하나 이상 있는 비율, Recall@5는 출발 파일별 정답 관련 파일 중 상위 5개가 회수한 비율의 평균, MRR@5는 첫 정답 순위의 역수(5위 안에 없으면 0)의 평균이다. Macro F1은 클래스별 정밀도·재현율의 조화평균을 동일 가중 평균한 값이다. 정확도, 자동 확정률, 신뢰도, 처리 커버리지는 서로 다르다.

이 절은 실험·검증 묶음 13개로 구성한다. README가 계획한 Precision@1/3/5, Hit@1/3 또는 독립 최종 평가 수치는 산출물이 확인되지 않아 새로 만들지 않았다. 관계 평가는 실제 코드에 있는 Hit@5·Recall@5·MRR@5만 사용한다.

### 4.1 실험 1 — 의미 검색 후보 재정렬

**실험 목적:** 비슷한 코드·강의가 경쟁하는 상황에서 상위 결과를 개선한다.

**기존 방식 및 문제점:** 파일 내 최대 청크 유사도만 사용한다. 특정 부분의 유사도만 높거나 동명·유사 파일이 경쟁하면 정답이 밀린다.

**실험 방법:** 동일 질의 임베딩과 입력으로 기본 순위와 재정렬을 함께 계산했다. 상위 30후보에 `0.85×최고 청크 + 0.15×상위 3청크 평균 + 0.04×파일명 일치`를 적용했다. 저장 결과는 정답 ID 기준 158질의이다.

| 조건 | 성공/전체 | Hit@5 |
| --- | ---: | ---: |
| 재정렬 CSV 안의 기본 검색 | 129/158 | 81.65% |
| 재정렬 | 129/158 | 81.65% |

**결과 해석:** 재집계상 실패→성공 1개와 성공→실패 1개가 상쇄되어 평균 개선은 없었다. 실패 순위 진단 29건은 재정렬 후 6~10위 8건, 11~30위 9건, 31위 이하 12건이다. 마지막 집단은 상위 후보 재정렬만으로 회수하기 어렵다. 평가 결과를 보며 가중치를 조정하는 코드이므로 독립 최종 평가가 아니다.

근거: [실험 코드](../Role01/search_model_rerank.py), [결과](../Role01/evaluation_results_rerank.csv), [진단](../Role01/failed_query_rank_diagnosis.csv).

### 4.2 실험 2 — 검색 passage에 description 추가

**실험 목적:** 본문의 표현만으로 검색하기 어려운 파일에 목적·내용 설명을 보완한다.

**기존 방식 및 문제점:** 본문·파일명·프로젝트·역할 입력만으로는 일부 데이터·코드의 질문 표현을 잘 포착하지 못했다.

**실험 방법:** E5·청크 500/80·파일별 최고점·Top5를 유지하고 각 passage에 설명을 추가했다. 두 CSV의 158개 질의와 정답 ID가 같은 것을 대조했다.

| 보존 결과 | 성공/전체 | Hit@5 |
| --- | ---: | ---: |
| 설명 없는 기본 결과 | 129/158 | 81.65% |
| 설명 포함 | 158/158 | 100.00% |

**결과 해석:** 이 보존된 질문 집합에서는 18.35%p 차이가 있다. 10월 29일 설명 포함이 운영 엔진에도 반영되었다. 다만 당시 수동 설명과 질문이 같은 데이터셋을 설명하며, 작업 단위 미사용 최종 질문이라는 증거는 없다. 이 결과를 현재 204개 전체·외부 사용자 검색의 100% 성능으로 표현하지 않는다. Role02 생성 설명 A/B와는 입력·목적이 다른 실험이다.

근거: [설명 실험 코드](../Role01/search_model_description.py), [기본 결과](../Role01/evaluation_results.csv), [설명 결과](../Role01/evaluation_results_description.csv), [운영 반영 커밋](https://github.com/eunkyo00/AI-X/commit/97a4cc8e6a).

### 4.3 실험 3 — 자연어 시간 조건과 정답 ID 교정

**실험 목적:** 월·생성/수정 조건을 의미 유사도와 분리하고 잘못된 평가 식별자를 교정한다.

**기존 방식 및 문제점:** 연도 없는 “3월달” 등이 일반 의미 질의로 남고, 목록 변화 후 과거 ID가 다른 파일에 대응하는 사례가 있었다.

**실험 방법:** 날짜 파싱·기간 필터와 의미 질의 정리를 추가하고 실패 감사 및 정답표 백업을 보존했다. 같은 194질의의 두 결과 CSV를 집계하되 정답 ID와 검색 대상 변화도 확인했다.

| 보존 결과 | 질의 구분 | 성공/전체 | Hit@5 |
| --- | --- | ---: | ---: |
| `evaluation_results_time.csv` | 전부 semantic로 기록 | 185/194 | 95.36% |
| `evaluation_results_time_fixed.csv` | semantic | 169/171 | 98.83% |
| 같은 fixed 결과 | temporal | 23/23 | 100.00% |
| 같은 fixed 결과 | 전체 | 192/194 | 98.97% |

**결과 해석:** 두 파일의 질의 순서는 같으나 정답 ID는 171행에서 바뀌었다. 상위 후보에도 추가 강의자료가 나타나므로 동일 코퍼스의 통제 비교로 볼 수 없다. 95.36→98.97%를 시간 알고리즘만의 개선량으로 주장하지 않는다. fixed의 시간 질의 23개는 정답이 시간 조건과 일치한다고 기록되었다. 남은 실패는 “시계열 11주차 코드”, “시계열 3주차 코드” 두 질의이다. 상대 시간은 실행일에 의존하며 저장 결과에는 모든 실행 기준일이 명시되어 있지 않다.

### 4.4 실험 4 — 관련 파일 V3/V4/V5 비교

**실험 목적:** 의미 유사도에 프로젝트·역할·시간·참조·주차를 더했을 때 관련 파일 회수가 좋아지는지 확인한다.

**기존 방식 및 문제점:** V3는 E5 평균 벡터만 사용하여 주제가 비슷한 파일과 같은 주차·보완 역할 파일을 구분하기 어렵다.

**실험 방법:** `confirmed` 관계만 사용한다. 현재 정답표 72쌍 중 70쌍이 확정, 2쌍은 pending이다. 개발은 43쌍·출발 파일 23개, 검토는 27쌍·출발 파일 17개이다. 저장된 CSV 순서의 중복 없는 상위 5개로 채점하며 자기 자신은 정답에 없다.

| 분할 | 버전 | 출발 파일 수 | Hit@5 | Recall@5 | MRR@5 |
| --- | --- | ---: | ---: | ---: | ---: |
| development | V3 | 23 | 0.9130 | 0.8696 | 0.7442 |
| development | V4 | 23 | 0.9565 | 0.8913 | 0.8007 |
| development | V5 | 23 | 1.0000 | 0.9638 | 0.8514 |
| review_holdout | V3 | 17 | 0.8824 | 0.8431 | 0.8529 |
| review_holdout | V4 | 17 | 0.9412 | 0.8137 | 0.7706 |
| review_holdout | V5 | 17 | 0.9412 | 0.8725 | 0.8471 |

**결과 해석:** 검토 집합에서 V4는 V3보다 Hit가 높지만 Recall·MRR은 낮다. V5는 V4 대비 Recall·MRR을 회복했고 Hit는 같다. V5의 MRR은 여전히 V3보다 조금 낮다. 같은 주차의 정답이 많아 주차 규칙이 이 데이터셋에 적합하지만 일반 작업 복원으로 일반화할 증거는 부족하다.

### 6.5 남은 개선 방향

우선 평가용 데이터·ID·코퍼스·질문·실행일·모델·가중치를 묶어 고정하고, 기존 질문 보완과 독립 최종 평가를 분리해야 한다. 파일 단위 높은 분류 정확도를 작업·과목이 다른 실제 신규 자료에서 검증하고, 신규 과목 정답도 별도 검수할 필요가 있다. 관계 추천은 주차/주제 중심 정답뿐 아니라 무관한 동시기 자료·공유 파일·출력 관계를 포함해 정밀도와 오탐을 점검하는 방향이 README 계획과 맞는다.

구현 측면에서는 남은 HTTP 테스트 계약, 설명 생성기의 과거 시험 코드, Qwen/모델 버전 호환성, Windows GUI, 새 OCR 문서 처리, 강제 종료 복구가 확인 과제다. 이는 현재 해결 완료 사항이 아니라 코드·보고서에서 확인된 한계와 후속 검증 방향이다.

### 7.2 조사 범위와 제외 기준

기준 커밋의 499개 트리 항목을 열거하고, 최상위/Role README, 역할별 Python 구현과 평가·자동화·테스트, GUI의 Python/JavaScript·계약·통합 보고, CSV/JSON·SQLite·로그 및 `Role02.zip`의 내부 구성을 확인했다. 저장소의 Python 검색 대상 표본은 실행하지 않고 내용·구문을 확인하여 시스템 구현과 구분했다. ZIP 안의 과거 Role02 코드·평가 묶음은 현행 폴더와 중복되는 자료이며 별도 개발 성과로 세지 않았다. 원시 PDF·Office·대형 ZIP의 모든 페이지를 재판독하거나 모델 바이너리를 재학습한 조사는 아니다.

Git 커밋 날짜·경로 변경 이력과 주요 구현 diff를 대조했으며, 경로 이동만으로 새 알고리즘 버전을 만들지 않았다. 병합 커밋과 그 안의 원개발 커밋도 별도 성과로 중복 계산하지 않았다. 최상위 현재 README에는 초기 계획과 최신 설치 안내가 함께 있으므로 실제 상태는 코드·산출물·날짜별 보고서로 보완했다. [커밋 이력](https://github.com/eunkyo00/AI-X/commits/6606aee277c154051d3d94be07842b85bed1a687/)

확인 필요 또는 기록 없음으로 남긴 항목은 실제 주차별 개발일 전부, 개인별 기능 기여, 독립 키워드 기준선, 작업 단위 최종 평가/단서 제거 전체 결과, 실제 신규 과목 정답 확정, 현재 204개 통합 검색 품질·반복 지연, Qwen 신규 생성의 최신 GUI 검증, Windows GUI 실기기 및 외부 사용자 사용성 평가이다. 보고서가 가리키는 로컬 `tmp` 캡처·검증 스크립트는 현재 트리에 없는 경우 상대 링크를 만들지 않았다.
